# Windows 11 Notepad insertion incident and benchmark readiness

Observed 2026-10-18 on an interactive Windows build 26200 desktop (session 1).
This is a host observation, not a universal reliability claim. Use only synthetic
text when reproducing; no real clipboard or dictation content belongs in logs.

## Concrete failure mechanism

| Evidence | Interpretation |
| --- | --- |
| A fresh Notepad top-level `Notepad` HWND exposed `Windows.UI.*` bridge children and a `RichEditD2DPT` document child on a different UI thread. | The top-level handle is not the editable document. The document was readable via `WM_GETTEXT` once initialized; assuming legacy `Edit` is incorrect. |
| Before the fix, a repeated eight-cycle synthetic probe dispatched all eight `Ctrl+V` chords but only four tokens appeared in the rich-edit document. | `SENT_UNVERIFIED` meant only that keys were sent, not that paste landed. |
| Focus metadata showed some failed cycles had `Windows.UI.Input.InputSite.WindowClass` focused instead of `RichEditD2DPT`; one had unrelated `chrome.exe` foreground. | Focus drift/foreground theft was the dominant observed missed-paste mechanism. `_safe_set_foreground()` also tried to set child focus while attached to the top-level thread, not the document child's thread. |
| The old `read_window_buffer()` could return text from FlowPilot's own clipboard while the rich-edit document remained empty. | The clipboard-copy fallback was false physical confirmation and could itself disturb selection, focus, and clipboard restoration. |
| Clipboard sequence advanced normally, with no copy exceptions; the verifier never invoked UIA. | Neither clipboard lock contention nor a delayed UIA event is supported as the root cause of these reproductions. |

The pre-fix chain was: target top-level HWND check -> forced foreground and guessed child focus when needed -> clipboard backup -> `pyperclip.copy` -> `keybd_event(Ctrl+V)` -> optional verification (off by default) -> `SENT_UNVERIFIED` -> 1.5-second sequence-guarded clipboard restore. The separate test verifier tried child `WM_GETTEXT`, then destructive `EM_SETSEL/WM_COPY` or global `Ctrl+A/Ctrl+C`; either fallback could read stale clipboard data or change the next paste's focus. The initial foreground check also preceded clipboard work, leaving a time-of-check/time-of-use gap before the key chord.

The patch preserves focus when the target is already foreground, stops forcing a guessed edit child when recovering foreground, checks foreground again immediately before dispatch, and uses bounded, non-invasive `WM_GETTEXT` on a real child edit control for physical confirmation. An opaque/unreadable target remains **unverified**; it is not pronounced successful because its clipboard contains the dictated text. The physical Notepad harness now focuses its *owned synthetic document* through that child's UI thread and permits one retry only after an independently readable document proves the unique test phrase absent. Production never auto-retries an opaque `SENT_UNVERIFIED` paste.

The targeted 18-scenario specification suite passed after the patch. A three-window, 15-cycle Notepad stress run completed with 15/15 physically present; **2/15 needed a proven-absent retry**. A later full regression gate passed **38/38 suites** in 102.21 seconds on October 19, 2026 after a fresh-window readiness fix. Earlier runs exposed intermittent focus and Notepad document-readiness failures; they are not erased by this pass. These are recovery and regression results, not 99.9% first-pass evidence. A larger target-app matrix and hundreds of paired trials are still required.

## Wispr behavior: observation boundary

Wispr's own Windows help says desktop insertion uses the system clipboard, restores the prior copy after about 0.5 seconds, holds dictation for about 3 seconds in Outlook/Word/WhatsApp, and about 5 seconds in supported remote-desktop viewers. It offers Paste Last Text and manual clipboard recovery when insertion fails. These disclosures support a clipboard-first, target-aware dwell/recovery model. They **do not** establish whether Wispr additionally uses `WM_CHAR`, UIA `ValuePattern`, or other internal fallbacks; no decrypted Wispr traffic or source trace was obtained in this investigation. See [pasting limitations](https://docs.wisprflow.ai/articles/1621472516-flow-fails-to-detect-text-fields-or-inserts-incorrectly-on-non-qwerty-keyboard-layouts), [terminal/remote behavior](https://docs.wisprflow.ai/articles/6478598909-using-flow-with-linux-wsl-and-terminal-applications), and [paste recovery](https://docs.wisprflow.ai/articles/7971211038-fix-text-not-pasting-after-dictation).

Do not pivot to UIA `ValuePattern.SetValue` as the universal insertion path. Microsoft's [WinUI automation documentation](https://learn.microsoft.com/en-us/windows/apps/dev-tools/winapp-cli/ui-automation) says WinUI 3 `RichEditBox` exposes read-only `TextPattern` and no settable `ValuePattern`; `send-keys` is required for such controls. UIA is useful for read-only focused-field discovery and confirmation where supported, but can block and must run behind a bounded worker process if added to the latency-sensitive path.

## Decision and follow-up units

1. **Current patch (completed):** keep clipboard/keyboard paste, non-invasive Win32 confirmation, foreground recheck, and the test-only document focus/recovery harness. The full 38-suite gate passed; never call this 99.9% reliability.
2. **Next 2-3 engineering days:** add an explicit in-memory paste attempt record and target-aware clipboard dwell, with a user-visible Paste Last action. Automatically retry only before any key dispatch or after a supported document reader proves absence; manual confirmation for opaque Electron/browser editors. Measure duplicates separately from misses.
3. **Next 3-5 engineering days plus test time:** build a Windows UIA read-only adapter in a disposable worker process with a 500 ms deadline and password-field exclusion; use it for context/verification only where supported. Benchmark Notepad, VS Code, Windows Terminal, browsers, remote desktops, and elevated windows under identical synthetic input. Do not promise 99.9% until at least 1,000 attempted pastes per target class establish a meaningful upper bound on misses and duplicates.

## Machine/tooling constraints

The shell is in interactive session 1 but is **not elevated**. `mitmproxy` 11.0.2 was installed in Git-ignored `scratch/benchmark-tools`; it listens only on `127.0.0.1:8899` for this session and successfully proxied a public HTTPS test request using a command-scoped CA file. Its generated CA SHA-1 thumbprint is `4EEF6A364073F87CD74D5CE86674A6998F6962D5`. The CA was **not** added to Windows trust: a request to persistently trust it for the current user was rejected because that broadens TLS interception trust for every user-level client. No global proxy setting was changed. Wispr routing, TLS decryption, endpoint schemas, payloads, sample rates, and context-canary transmission remain unmeasured.

The official VB-Cable Pack45 ZIP was staged under the same ignored directory. SHA-256: `B950E39F01AF1D04EA623C8F6D8EB9B6EA5C477C637295FABF20631C85116BFB`. The setup EXE has a valid Burel Vincent signature and the Windows 10 driver catalog a valid Microsoft Hardware Compatibility Publisher signature. After administrator/UAC installation, its WASAPI playback and recording endpoints appeared and passed a one-second 48 kHz synthetic-tone loopback check (captured RMS 0.11177, peak 0.28185). No default audio device was intentionally changed, but a post-install snapshot found the cable selected as default output, so the physical output route needs rechecking. Reboot completion was not reverified in this record. Both dictation apps must explicitly select the cable recording endpoint before a fair same-audio trial. See [VB-Audio's installation instructions](https://vb-audio.com/Cable/index.htm) and [mitmproxy's certificate guidance](https://docs.mitmproxy.org/stable/concepts/certificates/).
